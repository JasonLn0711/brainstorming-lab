# 工程細節：從幾何到可維護的互動網站

返回[閱讀入口](README.md)；搭配[原站架構圖](02-original-architecture.md)。以下「原站」指來源清冊版本；「改造」是我們的設計。

## 幾何：一個模型如何拆成可重用的零件

**問題：**如何讓很多建築既有共同風格，又能各自表達主題？

Three.js 的 Geometry 決定形狀，Material 決定表面怎麼呈現，Mesh 結合兩者與變換。把基本方塊縮成窗戶、圓柱拉成樹幹，再加上球狀樹冠，就能用一組共用形狀描述很多場景。這個分工與官方 [Fundamentals](https://threejs.org/manual/pages/fundamentals.html) 的基本場景模型一致。

原站 `kit.js` 先建立共用幾何，再由 `part()` 收集形狀、位置、縮放、旋轉、色彩與 owner。`sceneSpecs` 用固定政策 ID 指向模型種類，`createPolicyModel()` 及 `extraModel()` 把主題轉成零件。這避免陣列重新排序時，內容被錯配到別的外觀。

`resolveIslandPlacements()` 檢查建物 ID；完整的手工 composition 可直接使用，缺少時改選有效的主要建物，再計算其餘位置。`slotLayout()` 在六角內部找可放位置，逐步縮小尺寸；找不到足夠空間會拋出 overflow。這是實際的布局保護，不是任意數量都能塞進一座島。

**改造：**同樣以穩定內容 ID 綁定模型，六島先各放最多三個代表入口；其他內容從列表閱讀。重要物件的輪廓與文字必須可辨識，不以縮小到看不清楚換取更多建物。

## Instancing：減少繪圖呼叫，仍保留語意

原站先收集零件，再依 geometry kind 與小型裝飾 LOD 分桶。`kit.build()` 對每桶建立 `InstancedMesh`，逐一設定 matrix 與 color。GPU 可用同一形狀畫出多個不同位置的實例；實際 draw call 還受材質、陰影 pass 與其他物件影響，不是全站只需要一次繪圖。

| 索引方向 | 原站用途 | 為何必要 |
| --- | --- | --- |
| owner → mesh/index/color | 選取後修改同一建物所有零件 | 一棟樓由許多不同形狀構成 |
| batch instanceId → items → owner | Raycaster 命中後找建物 ID | 一個 batch 包含許多建物 |
| 人物 mesh + instanceId → person | 點到頭、手或腿仍找到同一人 | 身體零件也分批繪製 |

原站還使用 polygon offset 與很小的固定尺寸擾動，處理共面零件閃爍。它們是特定模型堆疊的視覺修正，不是可以套用到所有精確幾何的通則。

**改造：**少量主建築先用各島 Group 組裝；樹木與重複道具只在同一島內批次化。島本身浮動時只動 parent Group，避免每幀重寫全世界所有 instance。這會增加少量 batch，但能保持浮動、選取與銷毀邊界清楚。只有測到 draw call 瓶頸才跨島合批。

## 點擊：螢幕位置如何找到三維物件

滑鼠在螢幕上是二維座標。程式先減去 canvas 左上角，再除以 canvas 寬高，轉成 x、y 各介於 −1 到 1 的 normalized device coordinates；Raycaster 從相機往這個方向投射，回傳交點。

原站 pointerdown 記錄起點，pointerup 位移超過 6 CSS px 時視為拖曳，不觸發選取。命中後依 `userData.type` 處理 buildingBatch、walker、flow、island。這避免旋轉視角時誤開卡片。這個門檻是原站值，不代表觸控操作已全面驗證。

**改造：**canvas 可點選，列表也可完成相同任務。使用較簡單的選取幾何包住地標，不要求使用者精準點到窄窗框。點選結果只回傳 ID；卡片內容由同一份公開內容資料解析，不從幾何名稱拼出文章。

## 名牌：為什麼標籤比想像中難

CSS2DRenderer 把空間座標投影到畫面，文字仍是 DOM。原站 `clipLabels()` 檢查控制列、卡片、側欄等矩形區域，依選取優先序、偏移候選與前次可見狀態決定保留標籤。對顯示與隱藏使用不同邊界，有助減少標籤在臨界位置反覆閃動。

代價是讀取 DOM 邊界、排序與碰撞檢查。城市密度越高，文字本身越可能成為 CPU 與可讀性成本。不能只計算 GPU 三角形就判定效能。

**改造：**全景最多六個島名；選島後才顯示該島三個地標名。桌面右側面板占固定區域，手機只開一個底部面板，事先保留相機安全區。高密度避碰演算法留到確有需求再加。

## 路網：線、人物與內容必須一致

原站每島環路有六個頂點與六個邊中點，島間橋接邊中點。每條邊以距離為成本；最短路徑形成點列與累積距離。人物更新時把行走距離落到某段，再在段的兩端插值。

多起點、多終點 flow 先展開分支，排除明列的 excludedEdges、同點與 `unverified_no_animation` 分支。人物角色與攜帶物來自 flow。展示中的小人是敘事圖示，不是實際政策執行進度或真實物流資料。

**改造：**六島沒有步行橋網，第一版使用少量三維 Bézier 航線。線表示「某技能支持某作品」或「某研究與某系統相關」；每條線都附可閱讀說明。動畫光點只是方向提示，不使用成長、進度或資源流量等沒有證據的隱喻。

## 日夜、光影與 shader

原站的時間 keyframe 同時控制天空、地平線、日光、半球光、夜間係數與水色。`env.setTime()` 插值這些值；太陽方向按十分鐘量化，降低陰影持續移動造成的視覺抖動。`env.update()` 更新 shader 時間與雲的橫移；太靠近相機的雲會被隱藏。

天空與水面使用 ShaderMaterial；建築與人物仍以共用幾何及常規材質為主。`PCFSoftShadowMap`、色彩空間與 tone mapping 是畫面的一部分，但精緻感也依賴比例、配色、構圖與留白。

**改造：**第一版固定柔和日光，重點是辨識度。島底岩體、植物、局部瀑布用幾何與有限動畫；不先加體積雲、全景 bloom、即時反射或完整日夜系統。夜景作為後續可選外觀，先通過文字對比與手機效能再啟動。

## 狀態與時間

原站同時存在場景選取、清單模式、HEART 篩選、時鐘、導覽、人物跟隨與鏡頭 fly。這些概念應分開理解；例如暫停時間不等於關閉卡片，取消相機動畫也不等於取消內容選取。

鏡頭 fly 在 800ms 內使用 cubic easing 插值相機與 target。使用者按下 canvas 時會中斷 fly。減少動態效果模式下可直接到目標，避免強制鏡頭移動。

**改造：**第一版只需 overview／island／item 三種選取，加上一個 mobile panel 狀態。內容選取是 UI state 的唯一來源；Three.js 回報選取意圖，不能另存一份會不同步的文章狀態。

## 搜尋與資料治理

原站搜尋對名稱或整個物件 `JSON.stringify()` 後做小寫字串比對，能涵蓋很多欄位，但也可能命中 ID、來源標記或其他不直接展示的值。輸入資料依靠同站 JSON，雖有文字 escape，未見完整 schema validation；因此不能把這個 HTML 字串組裝方式直接用在任意使用者輸入或外部 CMS。

資料中存在 `confidence`、`verification`、`readyToPublish` 等欄位；各顯示入口是否一致遵守需逐條核對。一般卡片使用 `quoteHTML()`；導覽 caption 另有自己的字串產生路徑。僅看到「發布狀態欄位」不能宣稱每個畫面都完成相同把關。

**改造：**搜尋只索引公開 title、summary 與 tags。Svelte 的文字插值處理一般內容；不引入外部 raw HTML。建立時檢查唯一 ID、連結目標與關係端點；只將公開內容放入 bundle。前端隱藏不是保密措施。

## 效能、手機與錯誤處理

| 已確認措施 | 能說明什麼 | 不能直接推論什麼 |
| --- | --- | --- |
| DPR 上限 high 1.75／medium 1.4 | 減少高像素螢幕填色量 | 任意手機都流暢 |
| 手機／窄螢幕預設 medium | 啟動時依裝置訊號選品質 | 已做持續自適應 FPS 調節 |
| 小道具距離 LOD | 遠景可省掉細節 | 所有模型都多層 LOD |
| dirty render | 沒變化時可跳過 render | RAF 和 CPU 完全停止 |
| reduced-motion 與 pause | 有控制動態的實作 | 所有模式均已無障礙驗收 |
| ResizeObserver | canvas 與相機可配合容器尺寸 | 轉向後每種卡片都不遮擋 |
| 底部 catch | 部分初始化錯誤有訊息 | JS 載入失敗時仍有完整政策閱讀體驗 |

390×844 瀏覽器視窗查核時，在已開協作卡的狀態切到手機尺寸，底部清單與卡片同時占位。這是本次特定狀態轉換的觀察，尚未證明手機冷啟動也相同。它提示我們採單一 mobile panel，並測試桌面轉手機、開卡後搜尋、關閉再返回等組合。

## 維護評估與採用清單

保留：資料驅動畫面、穩定 ID、原始來源連結、幾何零件重用、列表與 3D 並行、關係線有語意。

調整：把 UI 與場景協調拆開；相機策略與標籤數量先簡化；路線改成三維；將公開內容與顯示狀態集中；以 route teardown 管理 GPU 資源。

暫緩：人物群體、導覽影片式時序、真實時間同步、自由飛行、複雜 shader、後台 CMS、即時 Notion 同步。每一項都需要具體訪客任務或實測瓶頸才重新開啟。

原站是完整產品案例，也有長主控檔、硬編碼視覺座標及多段 CSS 覆寫。學習目標是理解它如何解題，再依我們六島與既有 SvelteKit 的規模決定結構；不把所有功能一併搬入。
